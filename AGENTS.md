# Engineering principles

1. Every line of code should justify its existence. Define once; reuse everywhere.
2. Keep the site static and accessible. Prefer HTML/CSS/vanilla JS. Add dependencies only when a real requirement justifies them.
3. Four editorial categories only: postgraduate exam, overseas study, employment, civil service/public institutions. Experiences include guidance; do not create a separate guide category.
4. `data/schema.json` owns category labels and submission fields. Never duplicate category definitions in multiple scripts. Article titles are derived from author, destination, and optional program; do not request a redundant title from contributors.
5. Never pass invented student stories, admission results, testimonials, or counts off as real. Fictional editorial examples are allowed only with `demo: true` and a visible「演示」badge, never invented verifiable credentials or outcomes.
6. No hidden submission side effects. Never claim a submission succeeded until the backend confirms it.
7. Public GitHub Issues expose submitted content including optional contact details. Show a plain-language warning next to the form.
8. Use semantic markup, keyboard-accessible controls, responsive layouts, reduced-motion support, and readable contrast.
9. Browser previews and published pages must reuse `.article-page`, `.article-body`, headings, byline, and TOC structure. Preserve an automated browser comparison against published Markdown and do not add preview-only typography overrides. Use the same native collapsible article table of contents in preview and publication; highlight reading position without custom framework dependencies. Client Marked and server Python Markdown remain different parsers; document unsupported edge syntax rather than claiming byte-identical HTML. Changes should solve root causes, not accumulate patches. Commit coherent milestones directly to main during the initial build phase; PRs are not required.
10. The emergency-blue palette is a custom interpretation until official UEM visual identity color values are verified.

11. Use the original `assets/images/favicon-横版.png` as a single, undistorted header logo on desktop and mobile. Do not split, recompose, mask, or clip that logo. Use `assets/icons/favicon.svg` for browser favicons and the footer emblem, without an extra white CSS background or padding, and `assets/images/anguo-garden.jpg` as a dedicated top banner shared by homepage, submission and published article routes. Keep the image aspect-ratio intact with CSS `background-size: cover` and responsive cropping (never `100% 100%` or fixed full-page backgrounds). The main content remains a solid light/dark theme surface; the desktop content has no separate topbar, mobile navigation uses a dedicated 72px topbar above the banner with a stable, anchored menu panel, and a single system/light/dark theme switch (including matching icons) belongs at the bottom of the shared left sidebar; restore saved theme before stylesheet rendering with theme-init.js; disable cross-document root View Transitions; on every real internal navigation synchronously dismiss the mobile menu in a transition-free navigation reset state (including pagehide and BFCache pageshow), never retain an open outgoing panel; generate HAI-inspired footer navigation from the homepage and schema; retain transparent content and no decorative hero widgets. Keep image references consistent on root and generated article pages.


## Project structure and development

- Root `index.html` and `submit.html` are directly editable UI sources. Keep `assets/`, `content/`, `data/`, `scripts/` and `tests/` organized by their actual project responsibilities. The independent Worker accepts public Issues only after explicit launch. The maintainer-only Completed closure importer owns reviewed Markdown publication; never bypass GitHub review.
- `preview.py` provides local preview and verified artifact replacement; `scripts/site_build.py` runs this project's content pipeline in isolation. Publish `_site/` only. Shared page chrome is drawn from the homepage during generation; do not add a separate framework merely to make this repository resemble another site.
- Pagefind indexes only published article bodies from the generated `_site/` build and is lazy-loaded for full-text search. Keep category/year filters as UI intersection, not a second hand-maintained text index. A compact, keyboard-operated native Popover may enhance the year selector, but preserve a native select fallback and a single source of year options. Textareas should grow with contents using CSS field-sizing and a tiny legacy fallback, never separate drag handles. Markdown sample insertion must leave the editor visible and show syntax guidance; do not force a preview transition. Schema owns required fields, limits and patterns. Keep the Worker fail-closed by default in version-controlled configuration and preserve the Cloudflare emergency kill switch. The public front-end config identifies the trusted endpoint and public Turnstile Site Key; production launch state is controlled by Cloudflare secrets and environment variables, never client-side security alone.
- Run `python -m unittest discover -s tests -t . -p 'test_*.py'`, `python preview.py --build-only` and `python tests/browser_smoke.py` for structural/UI changes. Each repository can evolve independently after this quality alignment.
- Treat cross-project alignment as a quality baseline, not a fixed repository template. Prefer familiar, purpose-driven organization; reuse proven logic only when it suits this project. Each site may evolve its UI, dependencies and structure independently.
